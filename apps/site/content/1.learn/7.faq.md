## Testing

### Do I need a hosted service?

No. Playwright, Vitest, jest-image-snapshot, BackstopJS, Roborazzi and pixsame keep baselines in your repository and compare them on your own machines. A hosted service buys you a review interface, history and baselines that are off the repository, at a price per screenshot. [Baselines and approval](/learn/baselines-and-approval) has the trade-off and [the comparison](/compare) lists which tool does what.

### Should baselines be committed to git?

If the tool stores them next to the tests, yes: a branch then carries its own baselines, a revert reverts them and the pull request shows which images changed. The cost is repository size, which Git LFS addresses, and that every contributor has to render identical pixels. See [Where baselines live](/learn/baselines-and-approval#where-baselines-live).

### Why do my tests pass locally and fail in CI?

Almost always because the pixels are different, not the page: another operating system, another browser build, another font stack or another device pixel ratio. Pin the renderer first (a container image, or a cloud browser), then work through the rest in [Why screenshots flake](/learn/why-screenshots-flake) and the [cookbook](/cookbook). The [pin the renderer](/cookbook/pin-the-renderer) recipe covers this one.

### What threshold should I use?

The smallest one that makes a stable test pass, set on the screenshot that needs it and not globally, and only after the renderer is pinned and the noise is masked. A threshold that is raised early hides real changes. See [Thresholds last](/cookbook/thresholds).

### Which tool should I pick?

It depends on where you already test (Playwright, Cypress, Vitest, Storybook, a mobile project), on whether you want baselines in git or a service, and on what you are willing to pay for. [Choosing a tool](/learn/choosing-a-tool) walks through it and [the comparison](/compare) puts the tools side by side.

## The manifest and the viewer

### What is the run manifest?

One JSON file per test run that lists every screenshot comparison: its status, diff ratio, limits, the paths of the baseline, actual and diff images, and where the run happened. A review page or a pull request bot then reads one file instead of walking the snapshot folders. [The format](/manifest/format) describes it.

### Does my tool have to write a manifest?

No. For the tools that write none, [the converters](/manifest/converting) build one from what the tool leaves on disk. The `visual-regression-manifest convert <tool>` command runs them without a script:

```bash
npx visual-regression-manifest convert playwright report.json
```

### Which tools can be converted?

Playwright's `toHaveScreenshot`, Vitest's `toMatchScreenshot`, jest-image-snapshot, cypress-image-snapshot, cypress-visual-regression, cypress-image-diff-js, BackstopJS, Roborazzi, reg-cli and reg-suit, Lost Pixel and Loki, plus CTRF reports. The [pixsame](https://pixsame.com) Cypress plugin writes the manifest itself. For anything else, see [Write your own converter](/manifest/write-a-converter).

### How do I review a CI run?

Convert the run into a manifest if the tool does not write one, upload the folder as an artifact, and open it with the viewer:

```bash
npx visual-regression-viewer artifact.zip
```

The viewer accepts a folder, a manifest file or a zip. To publish a report instead, write it with `-o` and `--no-serve`. [The viewer's CI section](/viewer/cli#using-it-in-ci) has a GitHub Actions job that also fails on differences and writes the summary.

### Does the viewer send my screenshots anywhere?

No. The command makes no network requests and sends no telemetry. The page it builds is one self-contained HTML file. The [browser-only viewer](/viewer) reads the files you drop onto it in your browser and uploads nothing; see [privacy](/privacy).

### Which Node version do I need?

Node 20.9 or newer for `visual-regression-manifest`, and Node 22.12 or newer for `visual-regression-viewer`.

### Is the manifest an official standard?

Not yet. It is an open format with one maintainer, a JSON Schema and a reference library, built on [CTRF](https://ctrf.io) so it converts to a CTRF report and back. The aim is a format any tool can write and any review tool can read, and [the repository](https://github.com/visual-regression/visual-regression) welcomes changes to it.

## About this site

### Who maintains this?

The [pixsame](https://pixsame.com) team maintains it and the code is MIT licensed. The site is meant to stay useful to every visual regression tool, not only pixsame: corrections, comparison entries and converters for other tools are welcome through a pull request or an issue, as [CONTRIBUTING](https://github.com/visual-regression/visual-regression/blob/main/CONTRIBUTING.md) describes.
