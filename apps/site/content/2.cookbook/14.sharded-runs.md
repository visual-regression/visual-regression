## Symptom

The suite was sharded for speed and now every shard has its own idea of the baselines: one shard updated an image, another compared against the old one, the HTML report shows a quarter of the tests, and a reviewer has to open four CI jobs to find the failures. In the worst case, two shards run the same test (because the split is by file and the file is in both) and produce two different results for it.

## Fix

Shards may split the *work*; they must share the *baselines* and merge the *results*.

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  Each shard runs a slice of the tests and writes a blob report; one job merges them. Replace `<your Playwright version>` in the image tag with your installed `@playwright/test` version:

  ```yaml [.github/workflows/visual.yml]
  jobs:
    test:
      runs-on: ubuntu-latest
      container: mcr.microsoft.com/playwright:v<your Playwright version>-noble
      strategy:
        matrix: { shard: [1, 2, 3, 4] }
      steps:
        - uses: actions/checkout@v4
        - run: npm ci
        - run: npx playwright test --project=visual --shard=${{ matrix.shard }}/4
        - uses: actions/upload-artifact@v4
          if: always()
          with: { name: blob-report-${{ matrix.shard }}, path: blob-report }
    merge:
      needs: test
      if: always()
      runs-on: ubuntu-latest
      steps:
        - uses: actions/download-artifact@v4
          with: { pattern: blob-report-*, path: all-blob-reports, merge-multiple: true }
        - run: npx playwright merge-reports --reporter html ./all-blob-reports
  ```

  with `reporter: process.env.CI ? 'blob' : 'html'` in the config. The baselines are in the repository, so every shard checks out the same set; `fullyParallel: true` splits by test instead of by file, which balances shards better.
  :::

  :::tabs-item{label="Cypress"}
  Cypress's built-in `--parallel` needs `--record` and Cypress Cloud; without it, [`cypress-split`](https://github.com/bahmutov/cypress-split) splits the spec list across machines from `SPLIT` and `SPLIT_INDEX`:

  ```ts [cypress.config.ts]
  import cypressSplit from 'cypress-split';

  export default defineConfig({
    e2e: {
      setupNodeEvents(on, config) {
        initVisualRegressionPlugin(on, config);
        cypressSplit(on, config);
        return config;
      },
    },
  });
  ```

  ```yaml
  env:
    SPLIT: ${{ strategy.job-total }}
    SPLIT_INDEX: ${{ strategy.job-index }}
  ```

  `@pixsame/cypress-plugin-visual-regression-diff` stores baselines next to the specs, so each shard has every baseline from the checkout. On failure it leaves a `.actual.png` beside the baseline; upload those (and the diff images) as artifacts from every shard and collect them in one job for review. Never run with `pluginVisualRegressionUpdateImages=true` on a shard; updating is a separate, un-sharded job ([pin the renderer](/cookbook/pin-the-renderer#update-baselines-from-ci)).
  :::

  :::tabs-item{label="Vitest"}
  Vitest shards the same way and merges blob reports:

  ```sh
  vitest run --project visual --shard=1/3 --reporter=blob
  vitest run --project visual --shard=2/3 --reporter=blob
  vitest run --project visual --shard=3/3 --reporter=blob
  vitest run --merge-reports --reporter=html
  ```

  Reference screenshots live under `__screenshots__` next to the tests, in the repository, so every shard sees the same ones. Keep `--update` out of sharded runs.
  :::

  :::tabs-item{label="Any tool"}
  BackstopJS has no sharding; `backstop test --filter=<regex>` runs a subset of scenarios, so a matrix of filters is a manual shard, each producing its own report under `backstop_data`. Hosted services handle parallelism on their side: snapshots from several machines land in one build as long as every machine identifies the same build, and each service's parallelization docs describe how to pass that identifier.
  :::
::

### One baseline set, in one place

Baselines in the repository are the simplest sharding story: every shard checks out the same commit, so there is nothing to synchronize. If baselines live elsewhere (an artifact store, a bucket, a hosted service), every shard must fetch the same revision before comparing, and the update step must run once, never per shard. A shard that updates "its" baselines while another shard compares against the old ones is the bug from the symptom.

### One result for the reviewer

Each shard produces a partial result; the reviewer needs the union. Runner reports merge as shown above. For the review step itself (a PR comment, an approval tool, the [viewer](/viewer)), have each shard write a [manifest](/manifest) and merge them with `mergeManifests` from `visual-regression-manifest`, which concatenates the entries of a run, keys them by screenshot, test file, platform and renderer, and lets a later CI attempt win over an earlier one for the same key. The [merging page](/manifest/merging) has the API; the [converters](/manifest/converting) produce a manifest per shard from Playwright's JSON report, Vitest's output or BackstopJS's report.

### Retries and attempts

A retry of a failed shard is a second attempt with the same baselines; its result should replace the first attempt's, not sit next to it. The runner's merge does this for its own report; `mergeManifests` does it for the manifest by preferring the later attempt. Keep retries at zero for visual tests while you are still removing flakes, or a flake that passes on retry disappears from the report and never gets fixed.

## Verify

Run the suite with one shard and with four; the set of failures must be identical, and the merged report must list every test exactly once. Change a baseline on a branch and run sharded: all shards must see the new image (no shard may pass against the old one).
