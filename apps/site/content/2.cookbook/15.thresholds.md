## Symptom

You have done the other recipes: the renderer is pinned, animations are off, time and data are frozen, the dynamic regions are masked. One screenshot still differs by a few hundred pixels in a way you understand and accept (a chart's anti-aliased line, a gradient, a third-party font that hints differently on two browser versions). Or, more often: the threshold was raised early, globally, "to make CI green", and now nobody knows what it hides.

## Fix

Every tool exposes two limits; the [learn chapter](/learn/how-image-diffing-works) explains them. The **color tolerance** decides whether one pixel counts as different; the **maximum diff ratio** decides how many different pixels fail the image. Raise the second, for one screenshot, with a reason. Leave the first alone unless you can say which color shift you want to ignore.

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  The per-call option overrides the config default; add the reason next to it:

  ```ts
  // the trend line is anti-aliased differently between Chromium builds; ~0.3% on the worst run
  await expect(page.getByTestId('chart')).toHaveScreenshot({ maxDiffPixelRatio: 0.005 });
  ```

  Keep the project default strict (`maxDiffPixels` and `maxDiffPixelRatio` are unset by default, which means zero differing pixels allowed) and let `threshold` stay at `0.2`. `maxDiffPixels` is the absolute form; when both are set, the stricter one wins.
  :::

  :::tabs-item{label="Cypress"}
  `maxDiffThreshold` is the maximum diff ratio (default `0.01`, 1% of the pixels); `diffConfig.threshold` is pixelmatch's color tolerance:

  ```ts
  cy.get('[data-testid=chart]').matchImage({
    // gradient banding differs between the two Chromium builds we test in; measured 0.4%
    maxDiffThreshold: 0.006,
    // pixelmatch's color tolerance; leave it at its default unless you can name the color shift
    diffConfig: { threshold: 0.01 },
  });
  ```

  For a stricter suite-wide default, set `pluginVisualRegressionMaxDiffThreshold` in `expose` (or `env` on Cypress before 15.10); `0` fails on any difference. The plugin's `diffConfig` defaults to `{ includeAA: true }`, unlike pixelmatch itself (`false`), so anti-aliased edge pixels count toward the ratio; set `diffConfig: { includeAA: false }` to have them detected and skipped first.
  :::

  :::tabs-item{label="Vitest"}
  ```ts
  await expect.element(page.getByTestId('chart')).toMatchScreenshot({
    comparatorName: 'pixelmatch',
    // see chart.visual.test.tsx header: plotted line, ~0.3% on the worst run
    comparatorOptions: { allowedMismatchedPixelRatio: 0.005 },
  });
  ```

  Vitest sets no default tolerance for mismatched pixels (any difference fails) and uses pixelmatch's `threshold: 0.1` for color. `allowedMismatchedPixels` is the absolute form; the stricter of the two applies when both are set.
  :::

  :::tabs-item{label="Any tool"}
  BackstopJS has `misMatchThreshold` per scenario, in percent (default `0.1`, meaning 0.1% of the pixels):

  ```json
  { "label": "chart", "url": "/stats", "misMatchThreshold": 0.5 }
  ```

  jest-image-snapshot takes `failureThreshold` with `failureThresholdType: 'percent'` (the default type is `'pixel'`, and the default threshold is `0`). The hosted services expose one knob each (Chromatic's `diffThreshold` per story, Argos's `threshold`, Percy's diff sensitivity, Applitools' match level), described in the [deep dive](/deep-dives/diff-engines#hosted-and-layout-aware-comparison).
  :::
::

### Ratio, not pixels

Prefer the ratio form everywhere. `100` pixels is half of a 20×10 icon and nothing in a 1280×4000 page; `0.5%` means the same thing in both. A pixel count only makes sense when the screenshot's size is fixed and the tolerated region is known ("the 40×12 timestamp may differ entirely" is 480 pixels, and then a [mask](/cookbook/mask-dynamic-regions) is the better tool anyway).

### How to pick the number

1. Run the test ten times on the pinned renderer and once on each other environment you compare in.
2. Read the differing-pixel count of the worst run (the tool prints it; the [manifest](/manifest) stores it as `comparison.diffRatio`).
3. Set the limit just above it (worst run × 1.5, not a round number) and write the measurement in the comment.
4. Break something visible on purpose (a color, a label) and confirm the test still fails under the new limit. If it does not, the limit is too high and the screenshot too small for the change; split the screenshot or test the detail in a unit test.

### What a threshold must never be used for

- **Font or OS rendering noise.** It grows with the amount of text, so no single ratio fits every page, and whatever you pick hides a one-word typo on a text-heavy page. [Pin the renderer](/cookbook/pin-the-renderer).
- **Layout shifts.** A shifted block changes every pixel it covers; the ratio needed to tolerate it also tolerates a missing block.
- **Globally.** A suite-wide `maxDiffPixelRatio: 0.05` means every screenshot may lose 5% of itself unnoticed. Exceptions are per screenshot, with a comment, and reviewed when the cause goes away.
- **Instead of a review.** A high threshold that makes CI green is the same as deleting the test, with the cost of still running it.

### The color tolerance

Touch it only for a color reason: a slight tint difference between two GPUs, color-management differences between two browser versions. Note that it is the per-pixel scale of the engine (pixelmatch's `threshold` is `0.1` by default and `0.2` in Playwright; Resemble.js uses per-channel tolerances; looks-same a CIEDE2000 distance), so `0.1` means something different per tool. The [deep dive on types of visual diffing](/deep-dives/diff-engines) explains the scales. Lowering it toward `0` turns anti-aliasing into differences; raising it toward `1` accepts black for white.

### Write it down

A limit without a reason is a limit nobody dares to lower. The comment next to the option, the measurement it came from and the date are the minimum; the [manifest](/manifest) records the limit (`comparison.maxDiffRatio`) and the measured ratio next to each entry, so a reviewer sees "0.3% allowed, 0.1% measured" and a dashboard can list every screenshot whose exception is wider than it needs to be.

## Verify

After raising a limit, run the broken-on-purpose check from step 4 and ten clean runs. Then schedule a revisit: when the cause is fixed (the chart library disables animation, the renderer is pinned), lower the limit back and see the test still pass.
