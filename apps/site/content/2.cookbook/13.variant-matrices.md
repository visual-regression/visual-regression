## Symptom

Not a flake, a maintenance problem that turns into flakes: the same test copied for light and dark, then for RTL, then for three viewports, until a change to the test has to be made twelve times and the copies drift. Or the opposite: one baseline for a page that is captured in dark mode on one machine and light on another, because the scheme follows the OS.

## Fix

Write the test once, make the variant a parameter, and give every variant its own baseline whose name says which variant it is.

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  Projects multiply the suite by a `use` block each, and `{projectName}` lands in the snapshot name automatically:

  ```ts [playwright.config.ts]
  export default defineConfig({
    projects: [
      { name: 'desktop-light', use: { ...devices['Desktop Chrome'], colorScheme: 'light' } },
      { name: 'desktop-dark', use: { ...devices['Desktop Chrome'], colorScheme: 'dark' } },
      { name: 'phone-rtl', use: { ...devices['Pixel 7'], locale: 'ar', colorScheme: 'light' } },
    ],
    snapshotPathTemplate: '{testDir}/__screenshots__/{projectName}/{testFilePath}/{arg}{ext}',
  });
  ```

  One test, three projects, three baselines: `__screenshots__/desktop-dark/home.spec.ts/home.png` and so on. Run one variant with `--project=desktop-dark`.

  For a variant that is not a context option (a theme chosen in the app), loop inside the file instead and put the variant in the screenshot name:

  ```ts
  for (const theme of ['light', 'dark'] as const) {
    test(`home in ${theme} theme`, async ({ page }) => {
      await page.emulateMedia({ colorScheme: theme });
      await page.goto('/');
      await expect(page).toHaveScreenshot(`home-${theme}.png`);
    });
  }
  ```

  Text direction comes from the app (`<html dir="rtl">`), usually from the locale; set `locale` and let the app switch, or set `dir` with `page.addInitScript` when the app reads it from a setting.
  :::

  :::tabs-item{label="Cypress"}
  Loop over the variants and use the `title` option so each baseline carries its variant; drive the variant through the app's own switch (an attribute, a storage key, a query parameter):

  ```ts
  for (const theme of ['light', 'dark']) {
    for (const [name, w, h] of [['desktop', 1280, 720], ['phone', 375, 667]] as const) {
      it(`home, ${theme}, ${name}`, () => {
        cy.viewport(w, h);
        cy.visit('/', { onBeforeLoad: (win) => win.localStorage.setItem('theme', theme) });
        cy.matchImage({
          title: `home-${theme}-${name}`,
          screenshotConfig: { capture: 'viewport' },
        });
      });
    }
  }
  ```

  Cypress has no `colorScheme` option; the app-level switch is the portable way (a CDP `Emulation.setEmulatedMedia` call works in Chromium-family browsers but is not part of Cypress's documented API). For RTL, visit the RTL locale's URL or set `document.documentElement.dir` in `onBeforeLoad`.
  :::

  :::tabs-item{label="Vitest"}
  `test.each` over the variants, with the variant applied to the document and put in the screenshot name:

  ```ts
  test.each(['light', 'dark'] as const)('card in %s theme', async (theme) => {
    document.documentElement.dataset.theme = theme;
    render(<Card />);
    await expect.element(page.getByTestId('card')).toMatchScreenshot(`card-${theme}`);
  });
  ```

  For the `prefers-color-scheme` media query itself, a second browser instance with `contextOptions: { colorScheme: 'dark' }` runs the whole file again; give the instance a `name` and add it to the file name through `resolveScreenshotPath`, which receives the `browserName`, `platform` and `project` of the run.
  :::

  :::tabs-item{label="Any tool"}
  BackstopJS multiplies scenarios by `viewports` on its own, and the viewport label is part of the file name. For themes, add a scenario per theme with a query parameter the app understands (`/?theme=dark`) or an `onReady` script that sets the attribute.

  Storybook makes the variant a **global** (theme, direction, locale) that a decorator applies, and hosted services multiply stories over them: Chromatic's `modes` parameter takes a set of globals plus a viewport and captures each as its own snapshot.

  ```ts [.storybook/preview.ts]
  export const globalTypes = {
    theme: { toolbar: { title: 'Theme', items: ['light', 'dark'] } },
  };
  export const initialGlobals = { theme: 'light' };
  ```
  :::
::

### Rules that keep a matrix sane

- **The variant is in the name, always.** `home-dark-phone.png` next to `home-light-desktop.png`, never two `home.png` in different folders you have to diff mentally. Playwright's `{projectName}`, Vitest's `browserName`/`platform`, BackstopJS's viewport label and pixsame's `title` all exist for this.
- **Do not multiply everything.** A matrix of 3 themes × 2 directions × 4 viewports × every page is 24 baselines per page, which nobody reviews. Capture every page in the default variant, and the components that actually change (navigation, forms, data tables) in the others.
- **Make the default explicit.** A test without a variant is still a variant: say `colorScheme: 'light'` so it does not follow the OS of whoever records.
- **One recording environment** per variant, same as [pinning the renderer](/cookbook/pin-the-renderer): a dark-mode baseline from a Mac and a light-mode one from Linux is two problems.
- **Let the manifest carry it.** When the result is written as a [manifest](/manifest), the variant belongs in the entry's name and the environment in `platform` and `renderer`, so a review tool can group the same screen across variants.

## Verify

Run each variant alone (`--project`, `--grep`, `-t`) and all together; the baselines must be the same files. Turn the OS theme of your machine to the opposite of the tested one and run again: nothing may change.
