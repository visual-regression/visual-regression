## Symptom

Everything is shifted by a few pixels horizontally: a scrollbar appeared, or disappeared, and the content reflowed by its width. Or the actual image is twice the size of the baseline (a Retina laptop recorded it at device pixel ratio 2, CI compares at 1) and the tool reports a dimension mismatch. Or a full-page screenshot is a different height every run because content below the fold had not loaded yet.

## Fix

### Set the viewport and the scale factor explicitly

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  Both are context options; Playwright defaults to `1280×720` at `deviceScaleFactor: 1`, but say so, because a device preset (`devices['iPhone 13']`) changes both:

  ```ts [playwright.config.ts]
  use: { viewport: { width: 1280, height: 720 }, deviceScaleFactor: 1 },
  ```

  `toHaveScreenshot` captures at `scale: 'css'` by default, one image pixel per CSS pixel regardless of the device scale factor. If you want to test at DPR 2 (sharper text, different anti-aliasing), set `deviceScaleFactor: 2` and `scale: 'device'`, and keep it the same for recording and comparing.
  :::

  :::tabs-item{label="Cypress"}
  ```ts
  cy.viewport(1280, 720);
  ```

  or `viewportWidth` / `viewportHeight` in the config (the defaults are `1000×660`). Cypress does not simulate `devicePixelRatio`; a headed run on a high-density screen captures at the screen's ratio. `@pixsame/cypress-plugin-visual-regression-diff` forces the scale factor to 1 in Chromium-family browsers by default (`forceDeviceScaleFactor: true`), which is what makes `cypress open` and `cypress run` produce the same image. Cypress screenshots are `fullPage` by default; for a viewport-sized image:

  ```ts
  cy.matchImage({ screenshotConfig: { capture: 'viewport' } });
  ```

  A headless browser window smaller than the viewport cuts the capture; size the window in `setupNodeEvents`:

  ```ts [cypress.config.ts]
  on('before:browser:launch', (browser, launchOptions) => {
    if (browser.family === 'chromium' && browser.isHeadless) {
      launchOptions.args.push('--window-size=1280,720', '--force-device-scale-factor=1');
    }
    return launchOptions;
  });
  ```

  (Compose it with the plugin's own handler via `cypress-on-fix`, as the plugin README shows.)
  :::

  :::tabs-item{label="Vitest"}
  The viewport is a browser option (the default is `414×896`, a phone), the scale factor a Playwright context option:

  ```ts [vitest.config.ts]
  browser: {
    viewport: { width: 1280, height: 720 },
    provider: playwright({ contextOptions: { deviceScaleFactor: 1 } }),
  },
  ```

  Vitest recommends `browser.viewport` over a viewport in `contextOptions`, which is lost in headless mode. Per test, `await page.viewport(1280, 720)` changes it on the fly.
  :::

  :::tabs-item{label="Any tool"}
  BackstopJS takes a list and names each one; the label ends up in the file name:

  ```json [backstop.json]
  "viewports": [
    { "label": "phone", "width": 375, "height": 667 },
    { "label": "desktop", "width": 1280, "height": 720 }
  ]
  ```

  For a tool that only launches a browser, Chromium's `--window-size=1280,720` and `--force-device-scale-factor=1` switches do the same from the outside.
  :::
::

### Keep scrollbars out of the picture

Linux and Windows draw scrollbars inside the layout (and take about 15 px from it); macOS overlays them. Headless Chromium hides them (Chromium's `--hide-scrollbars` switch, which Playwright and pixsame's `deterministicRendering` preset use for headless runs), a headed browser does not, so a baseline recorded headed on a Mac and compared headless on Linux differs by a scrollbar's width in every scrolling container. Hide them with CSS in the test build, in the injected stylesheet, or in `stylePath`:

```css
html {
  scrollbar-width: none; /* Firefox, Chromium 121+, Safari 18.2+ */
}
::-webkit-scrollbar {
  display: none; /* older WebKit and Blink */
}
```

The page stays scrollable, only the bars are gone. Apply the same rule to inner scroll containers (`overflow: auto` panels), which have their own bars.

### Full-page screenshots and lazy loading

`fullPage: true` captures the whole scrollable height, but content with `loading="lazy"` or an intersection observer only loads when scrolled into view, so the bottom of the page is a different height, or empty, depending on timing. Scroll through the page before the capture and wait for the images:

```ts
// Playwright; the same loop works in page.evaluate for any tool
await page.evaluate(async () => {
  for (let y = 0; y < document.body.scrollHeight; y += window.innerHeight) {
    window.scrollTo(0, y);
    await new Promise((r) => setTimeout(r, 50));
  }
  window.scrollTo(0, 0);
});
await page.waitForFunction(() =>
  Array.from(document.images).every((img) => img.complete && img.naturalWidth > 0),
);
await expect(page).toHaveScreenshot({ fullPage: true });
```

Or make the test build eager (`loading="eager"`, observers that fire immediately under a test flag). Fixed headers and `position: sticky` elements repeat in a stitched full-page capture; hide them with the stylesheet or screenshot the main element instead. When a page is very long, a few element screenshots are easier to review than one tall image.

## Verify

Run the same test headed and headless, and on two machines with different screens. The images must be the same size (check the tool's dimension-mismatch error first) and the diff must be clean. Then `--repeat-each 10` for the full-page case; a varying height is the lazy-loading bug.
