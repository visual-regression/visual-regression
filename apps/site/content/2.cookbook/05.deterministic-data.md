## Symptom

The diff shows a different product in the first card, a list in another order, another avatar, a different "recommended for you". The page is correct both times; the data behind it was not the same. A smaller version: a single number differs, a stock count, a view counter, a random ID in a label.

## Fix

Decide per page what the test is about. If it is the UI, give it fixed data. If it is the integration with a real backend, seed that backend and give the test its own account. Both are fine; a page that fetches live production data is not.

### Mock the network

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  Fulfill the route with a fixture before the page loads:

  ```ts
  import products from './fixtures/products.json' with { type: 'json' };

  await page.route('**/api/products*', (route) => route.fulfill({ json: products }));
  await page.goto('/shop');
  await expect(page).toHaveScreenshot();
  ```

  To mock a whole flow, record it once into a HAR file and replay it:

  ```ts
  await page.routeFromHAR('./hars/shop.har', { url: '**/api/**', update: false });
  ```

  Run once with `update: true` to record. `context.route` instead of `page.route` covers popups and new pages too.
  :::

  :::tabs-item{label="Cypress"}
  ```ts
  cy.intercept('GET', '/api/products*', { fixture: 'products.json' }).as('products');
  cy.visit('/shop');
  cy.wait('@products');
  cy.matchImage();
  ```

  `cy.intercept` must be set up before the request happens, so before `cy.visit`. Fixtures live in `cypress/fixtures`.
  :::

  :::tabs-item{label="Vitest"}
  Components rendered in browser mode fetch through the real browser, so mock at the network layer with [MSW](https://mswjs.io/docs/integrations/browser):

  ```ts [tests/screenshot-setup.ts]
  import { setupWorker } from 'msw/browser';
  import { http, HttpResponse } from 'msw';
  import products from './fixtures/products.json' with { type: 'json' };

  const worker = setupWorker(
    http.get('/api/products', () => HttpResponse.json(products)),
  );
  await worker.start();
  ```

  Or pass the data as props and keep the fetching out of the component under test.
  :::

  :::tabs-item{label="Any tool"}
  Put MSW (or any request interceptor) into the app itself behind a build flag; the same mocked app then serves BackstopJS, Storybook, Lost Pixel and every other URL-based tool:

  ```ts [src/main.ts]
  if (import.meta.env.VITE_MOCK_API === 'true') {
    const { worker } = await import('./mocks/browser');
    await worker.start();
  }
  ```

  Storybook users have the same thing packaged as [`msw-storybook-addon`](https://github.com/mswjs/msw-storybook-addon). If the backend is yours, a seeded test database (one fixture set loaded before the run) makes the real API deterministic without any browser-side mocking.
  :::
::

### Seed the generators

Generated test data must be the same every run. Faker is seeded with one call; do it once in a setup file:

```ts
import { faker } from '@faker-js/faker';
faker.seed(123);
```

The sequence only changes when you upgrade Faker, which the project documents as a breaking change for seeded values; expect to re-approve baselines then.

### Seed `Math.random`

Anything in the page that rolls its own dice (random placeholder colors, a shuffled list, a sampled avatar) uses `Math.random`, which cannot be seeded. Replace it before the app runs with a small seeded generator:

```ts [tests/seeded-random.ts]
// mulberry32: tiny, deterministic, good enough for UI
export function seededRandom(seed = 42) {
  return () => {
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  ```ts
  await page.addInitScript(() => {
    let seed = 42;
    Math.random = () => {
      seed = (seed + 0x6d2b79f5) | 0;
      let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
      t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
      return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
    };
  });
  ```

  `addInitScript` runs before any script of the page, on every navigation.
  :::

  :::tabs-item{label="Cypress"}
  ```ts
  cy.visit('/', {
    onBeforeLoad(win) {
      win.Math.random = seededRandom(42);
    },
  });
  ```
  :::

  :::tabs-item{label="Vitest"}
  ```ts
  beforeEach(() => {
    vi.spyOn(Math, 'random').mockImplementation(seededRandom(42));
  });
  ```
  :::

  :::tabs-item{label="Any tool"}
  Give the app a seam again: in the test build, `Math.random` is replaced at startup, or better, the app takes its random source from one module you can swap. `crypto.getRandomValues` and `crypto.randomUUID` need the same treatment if the page uses them for anything visible.
  :::
::

### What not to mock

Do not mock what the screenshot is supposed to test. A component test that mocks its own rendering proves nothing. And do not mock time or data differently in two tests of the same page; keep one fixture set per page so the baselines stay comparable.

## Verify

Run the test with the network disconnected from the real backend (point `baseURL` at a port with nothing on it): it must pass if every request is mocked, and fail with an obvious empty page if one slipped through. Then run it ten times in a row.
