## Symptom

The diff shows a spinner where the baseline shows content, an empty list where the baseline has ten rows, a gray placeholder where an image should be, or a layout that jumps because a late image changed the height. The test passes locally and fails in CI, where everything is slower, or fails only when the runner is busy.

## Fix

Replace every fixed sleep with a wait for the thing you actually need. The page's `load` event fires before data arrives, before images decode and before frameworks finish hydrating, so "loaded" is the wrong signal.

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  Assert on the state that proves the page is done, then capture. Web assertions retry until they pass or time out:

  ```ts
  await page.goto('/orders');
  await expect(page.getByRole('row')).toHaveCount(10); // the data is in
  await expect(page.getByTestId('spinner')).toBeHidden(); // the loading state is gone
  await page.waitForFunction(() =>
    Array.from(document.images).every((img) => img.complete && img.naturalWidth > 0),
  ); // every image decoded
  await expect(page).toHaveScreenshot();
  ```

  To wait for one request, `await page.waitForResponse('**/api/orders')` before the assertions. `toHaveScreenshot` adds a last safety net: it takes screenshots until two consecutive ones are identical, which absorbs a frame of late rendering but not a request that has not returned.

  Playwright's docs mark `page.waitForLoadState('networkidle')` as **discouraged** for tests ("rely on web assertions to assess readiness instead"): it waits for 500 ms without network connections, which never happens on a page with polling or analytics and happens too early on a page that fetches in two rounds.
  :::

  :::tabs-item{label="Cypress"}
  Cypress commands retry their assertions, and `cy.wait` on an aliased intercept waits for the real response:

  ```ts
  cy.intercept('GET', '/api/orders*').as('orders');
  cy.visit('/orders');
  cy.wait('@orders');
  cy.get('[data-testid=spinner]').should('not.exist');
  cy.get('table tbody tr').should('have.length', 10);
  cy.get('img').should(($imgs) => {
    $imgs.each((_, img) => expect(img.naturalWidth, img.src).to.be.greaterThan(0));
  });
  cy.matchImage();
  ```

  `cy.wait(2000)` with a number is the fixed sleep; Cypress's own best-practices page lists it as an anti-pattern.
  :::

  :::tabs-item{label="Vitest"}
  `expect.element` retries like Playwright's assertions; `expect.poll` and `vi.waitFor` cover anything that is not an element:

  ```ts
  render(<Orders />);
  await expect.element(page.getByRole('row').nth(9)).toBeVisible();
  await expect.element(page.getByTestId('spinner')).not.toBeInTheDocument();
  await vi.waitFor(() => {
    for (const img of document.images) if (!img.complete || !img.naturalWidth) throw new Error(img.src);
  });
  await expect.element(page.getByTestId('orders')).toMatchScreenshot();
  ```

  `toMatchScreenshot` also retries the capture until two consecutive screenshots match (its `timeout` option bounds that).
  :::

  :::tabs-item{label="Any tool"}
  BackstopJS waits for a selector or a console message, which the app can emit when it is really done:

  ```json [backstop.json]
  { "readySelector": "[data-ready=true]", "readyTimeout": 30000 }
  ```

  ```ts [app]
  // after the data is rendered and the images decoded
  document.body.dataset.ready = 'true';
  console.log('app:ready'); // or readyEvent: "app:ready"
  ```

  `delay` exists too; use it only after the ready signal, for the last frame of a transition you could not disable. A ready marker set by the app is the most portable signal there is: every tool, including Storybook runners and hosted services, can wait for a selector.
  :::
::

### Why a fixed sleep fails

A sleep of N milliseconds is wrong in both directions. Shorter than the slowest run and the test flakes on a busy CI runner; longer and every run pays for the worst case, so a suite of 200 screenshots waits ten minutes for nothing. There is no N that is right on your laptop, on a cold CI container and on a throttled shared runner, and a sleep hides the real question: what, exactly, has to be true before the capture?

### What to wait for, in order

1. The response that carries the data (`waitForResponse`, `cy.wait('@alias')`), when the page fetches.
2. The element that only exists once the data is rendered (the tenth row, the heading with the order number).
3. The absence of loading states (spinners, skeletons, "loading..." text).
4. Decoded images and loaded [fonts](/cookbook/fonts).
5. A settled layout: an element's bounding box that does not change between two reads, if a late reflow is still a problem.

## Verify

Throttle the network and the CPU in the test (Playwright: route handlers with a delay, or a CDP `Network.emulateNetworkConditions` session; Cypress: `cy.intercept` with `delay`) and run ten times. The test must pass at the same rate as without throttling. If it only passes with a sleep, the sleep is standing in for a wait you have not written yet.
