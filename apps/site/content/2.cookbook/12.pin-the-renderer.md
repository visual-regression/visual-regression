## Symptom

Every text edge is highlighted, in every screenshot, by a pixel or two: the baseline was recorded on a Mac and compared on Linux (or on a different browser version, or with a different GPU). The diff ratio is small but never zero, the team keeps raising the threshold, and one day a real regression slides through under it. The [learn chapter](/learn/why-screenshots-flake#the-environment-renders-differently) calls this the single most common source of noise.

## Fix

Render in one environment, always: a container image with a pinned browser version and the fonts the app needs. Record baselines in it, compare in it, and make the test suite refuse to compare anywhere else.

### The image

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  Playwright publishes an image per release with the browsers installed. Replace `<your Playwright version>` with the `@playwright/test` version in `package.json`; with a different tag the runner cannot find its browsers:

  ```dockerfile [Dockerfile]
  FROM mcr.microsoft.com/playwright:v<your Playwright version>-noble
  # fonts the app relies on that are not in the image (emoji, CJK, a brand font)
  COPY tests/fonts/*.ttf /usr/local/share/fonts/
  RUN fc-cache -f
  WORKDIR /app
  COPY package.json pnpm-lock.yaml ./
  RUN corepack enable && pnpm install --frozen-lockfile
  COPY . .
  ENV PINNED_RENDERER=1
  CMD ["pnpm", "exec", "playwright", "test", "--project=visual"]
  ```

  Run it with `--ipc=host`, which Playwright recommends for Chromium ("Without it, Chromium can run out of memory and crash"):

  ```sh
  docker build -t app-visual .
  docker run --rm --ipc=host -v "$PWD/tests:/app/tests" app-visual
  ```

  The volume mount brings the updated baselines back out of the container. Without a Dockerfile, the same works ad hoc: `docker run --rm --ipc=host -v "$PWD:/app" -w /app mcr.microsoft.com/playwright:v<your Playwright version>-noble npx playwright test`.
  :::

  :::tabs-item{label="Cypress"}
  Cypress publishes `cypress/included:<cypress version>` (Cypress, browsers and OS dependencies) and `cypress/browsers:<node>-<chrome>-...` (browsers only):

  ```dockerfile [Dockerfile]
  FROM cypress/included:16.2.1
  COPY tests/fonts/*.ttf /usr/local/share/fonts/
  RUN fc-cache -f
  WORKDIR /app
  COPY package.json package-lock.json ./
  RUN npm ci
  COPY . .
  CMD ["npx", "cypress", "run", "--browser", "chrome", "--expose", "pluginVisualRegressionDeterministicRendering=true"]
  ```

  `@pixsame/cypress-plugin-visual-regression-diff` keeps baselines next to the specs (`{spec_path}/__image_snapshots__`), so a volume mount of the project brings them out. Its `deterministicRendering` preset (`--font-render-hinting=none --disable-font-subpixel-positioning --disable-lcd-text --force-color-profile=srgb --disable-gpu`, plus the injected CSS) is worth enabling even inside the container: it removes the browser's share of the noise, which also makes a developer's local run closer to the container's.
  :::

  :::tabs-item{label="Vitest"}
  Vitest's own guide says visual tests "are most reliable when run in a standardized and tightly controlled environment" and points at Playwright's Docker image. Use the same base:

  ```dockerfile [Dockerfile]
  FROM mcr.microsoft.com/playwright:v<your Playwright version>-noble
  WORKDIR /app
  COPY package.json pnpm-lock.yaml ./
  RUN corepack enable && pnpm install --frozen-lockfile
  COPY . .
  CMD ["pnpm", "vitest", "run", "--project", "visual", "--browser.headless"]
  ```

  The `playwright` package version inside the project must match the image tag here too.
  :::

  :::tabs-item{label="Any tool"}
  BackstopJS ships its own image and a flag that runs the engine in it: `backstop reference --docker` and `backstop test --docker` (the README: "this will help with consistency if you are attempting to compare references across multiple environments"). The `dockerCommandTemplate` config controls the `docker run` line.

  For any other tool, build from the browser vendor's image (`mcr.microsoft.com/playwright`, `cypress/browsers`, `selenium/standalone-chrome`) rather than installing a browser with `apt`, which gives you whatever version the distribution has that week.
  :::
::

### Fonts in the image

The browser image has a set of system fonts, which is not the set on your laptop. Self-hosted web fonts ([fonts recipe](/cookbook/fonts)) render the same everywhere; everything that falls back to a system font (`sans-serif`, `system-ui`, emoji, CJK) renders with whatever the image has. Copy the fonts the app needs into the image and run `fc-cache`. Pin the image tag (never `latest`): a font change in the base image is a baseline change for you.

### Compare only in the container

A developer running the suite on a laptop should get the functional results and skip the screenshot comparison, instead of a wall of font diffs. Playwright has a config option for exactly this:

```ts [playwright.config.ts]
export default defineConfig({
  ignoreSnapshots: !process.env.PINNED_RENDERER, // skip toHaveScreenshot outside the container
  projects: [{ name: 'visual', testMatch: /.*\.visual\.spec\.ts/ }],
});
```

Elsewhere, put the visual tests in their own project or spec folder and only run it from the container (and from CI, which uses the same image). pixsame users can set `pluginVisualRegressionUpdateImages=true` locally to keep going without comparing, but that overwrites baselines, so prefer not running the visual specs at all.

### Update baselines from CI

If baselines may only be recorded in the pinned image, "update the baseline" becomes a CI job, not a local command. The simplest shape: a workflow that runs the suite with the update flag (`--update-snapshots` in Playwright, `--update` in Vitest, `pluginVisualRegressionUpdateImages=true` in pixsame, `backstop approve`) and opens or pushes a commit with the changed images:

```yaml [.github/workflows/update-baselines.yml]
on: workflow_dispatch
jobs:
  update:
    runs-on: ubuntu-latest
    container: mcr.microsoft.com/playwright:v<your Playwright version>-noble
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx playwright test --project=visual --update-snapshots
      - run: |
          git config user.name baselines-bot && git config user.email bot@example.com
          git add '**/*-snapshots/*.png' && git commit -m "test: update visual baselines" && git push
```

Review that commit like any other: the [approval chapter](/learn/baselines-and-approval) covers the workflow, and a [manifest](/manifest) from the run gives the reviewer the list of what changed. Playwright's `--update-snapshots=changed` (the default when the flag has no value) updates only mismatches and creates missing ones.

### The fallback: one baseline per OS

When a container is not an option (no Docker in CI, tests on real devices, Safari), keep one baseline per environment you compare in and name it so:

- Playwright and Vitest do this by default: `-chromium-linux` / `-chromium-darwin` suffixes. Playwright's `snapshotPathTemplate` has `{platform}` and `{projectName}` tokens for custom layouts.
- pixsame: put `Cypress.platform` in `imagesPath` the way the README shows for the browser name, e.g. ``imagesPath: `{spec_path}/__image_snapshots__/${Cypress.platform}` ``.
- The [manifest](/manifest) records `platform` and `renderer` per entry, so a review tool can show the Linux and the macOS run of the same test side by side.

It costs one set of baselines per OS and a rule that every developer records on the OS they compare on, which is why the container is the better deal.

## Verify

Record the baselines in the container, then run the comparison twice from the container on two different hosts (your laptop and CI). Both must pass with zero differing pixels; a non-zero count that is "small" is the noise this recipe exists to remove. Run the same test outside the container once and confirm it is skipped rather than failing.
