## Symptom

A chart is different in every run: the bars are at a different height (the entry animation), the data points move (live data), or the diff is a faint speckle over the whole canvas while nothing visibly changed (the GPU rasterized the gradient or the anti-aliased lines slightly differently). WebGL scenes do the same, with the extra twist that `--disable-gpu` leaves them without a rendering context.

## Fix

A canvas is drawn by code, so it has no CSS to freeze and no DOM to wait for. Stabilize the code that draws it.

### Disable the library's animation

Every chart library has a switch. Set it from the same test flag you use for the rest of the app:

```ts
const ANIMATE = import.meta.env.VITE_SCREENSHOT_MODE !== 'true';

// Chart.js
new Chart(ctx, { type: 'bar', data, options: { animation: ANIMATE } });
// Apache ECharts
chart.setOption({ animation: ANIMATE, series });
// Highcharts
Highcharts.chart('c', { chart: { animation: ANIMATE }, plotOptions: { series: { animation: ANIMATE } } });
// Recharts
<Line isAnimationActive={ANIMATE} />
```

A library without a switch usually accepts a duration of 0. Tooltips, crosshairs and hover highlights are interaction state; keep the pointer off the chart ([hover and focus](/cookbook/hover-focus-caret)).

### Feed it fixed data

A chart of live data is a chart of noise. [Mock the series](/cookbook/deterministic-data) and [freeze the time axis](/cookbook/freeze-time): a time-series chart that ends "now" moves every second.

### Render on the CPU

GPU rasterization differs between machines and drivers. Chromium can render through SwiftShader, its software renderer, which gives the same pixels on every machine:

::tabs{sync="runner"}
  :::tabs-item{label="Playwright"}
  ```ts [playwright.config.ts]
  use: {
    launchOptions: { args: ['--use-gl=angle', '--use-angle=swiftshader'] },
  },
  ```

  Recent Chrome also needs `--enable-unsafe-swiftshader` for WebGL to fall back to SwiftShader. For 2D canvas only, `--disable-gpu` is enough. Playwright's Docker image already runs headless on the CPU; see [pin the renderer](/cookbook/pin-the-renderer).
  :::

  :::tabs-item{label="Cypress"}
  ```ts [cypress.config.ts]
  on('before:browser:launch', (browser, launchOptions) => {
    if (browser.family === 'chromium') {
      launchOptions.args.push('--use-gl=angle', '--use-angle=swiftshader', '--enable-unsafe-swiftshader');
    }
    return launchOptions;
  });
  ```

  `@pixsame/cypress-plugin-visual-regression-diff`'s `deterministicRendering` preset adds `--disable-gpu`, which its README warns may leave WebGL pages without a context; for WebGL, add the SwiftShader switches in your own `before:browser:launch` handler, composed with the plugin's via `cypress-on-fix`.
  :::

  :::tabs-item{label="Vitest"}
  ```ts [vitest.config.ts]
  provider: playwright({
    launchOptions: { args: ['--use-gl=angle', '--use-angle=swiftshader'] },
  }),
  ```
  :::

  :::tabs-item{label="Any tool"}
  BackstopJS passes switches through `engineOptions`:

  ```json [backstop.json]
  "engine": "playwright",
  "engineOptions": { "args": ["--use-gl=angle", "--use-angle=swiftshader"] }
  ```

  Any tool that launches Chromium itself accepts the same switches on its launch options; a hosted service renders on its own farm and you cannot change its GPU, which is one reason their comparison has tolerances built in.
  :::
::

### When a tolerance is the honest answer

Even with animations off, fixed data and a software renderer, a canvas can differ by a few hundred pixels: anti-aliased diagonal lines and gradients rasterize differently between browser versions, and pixel-level anti-aliasing detection is tuned for text edges, not for a plotted line. Then:

- Keep the color tolerance; raise the **maximum diff ratio** for *that* screenshot only (`maxDiffPixelRatio` in Playwright, `maxDiffThreshold` in pixsame, `allowedMismatchedPixelRatio` in Vitest, `misMatchThreshold` per scenario in BackstopJS), with a comment saying why. The [thresholds recipe](/cookbook/thresholds) has the rules.
- For charts with large flat areas and thin lines, a structural comparison is a better fit than a pixel count: jest-image-snapshot's `comparisonMethod: 'ssim'` compares local patterns of luminance, contrast and structure, which ignores sub-pixel line shifts but still catches a missing bar. The [deep dive on types of visual diffing](/deep-dives/diff-engines#structural-similarity) explains what SSIM sees and misses.
- Test the data separately. A unit test of the series going into the chart catches "wrong numbers" with no pixels at all; the screenshot then only has to prove the chart rendered.

Do not mask the whole chart: a masked chart cannot regress, and the chart is why the page exists.

## Verify

Run the test ten times on one machine and once on another (your laptop and CI). Count the differing pixels on the worst run and set the ratio just above it, not at a round number. Then change one data point in the fixture: the test must fail.
