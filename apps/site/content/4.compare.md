## Choosing a tool

There are more visual regression tools than any team needs and most of them are fine. The choice comes down to four questions about your situation.

### 1. What do you screenshot?

- Components in isolation (a design system, a Storybook): tools that render stories are the natural fit. Loki and the hosted services take a Storybook build. Pixsame (once its Playwright runner ships) will fit here too: Playwright can open a running Storybook and screenshot each story, so the runner's comparison and review apply to components as well as pages. Vitest browser mode and Playwright component tests screenshot components without Storybook.
- Pages and flows in a real browser: the screenshot assertion of your end-to-end runner (Playwright's `toHaveScreenshot`, a Cypress plugin) or a standalone crawler like BackstopJS that works from a list of URLs.
- Native screens: a per-platform tool (Roborazzi or Paparazzi on Android, swift-snapshot-testing on iOS, Flutter's golden tests, Maestro across both).

Most teams end up with two test suites: a component-level suite for the design system and a page-level suite for the key flows.

### 2. Where should comparison and review happen?

Local tools compare on the machine that ran the tests and leave images on disk. You own everything, pay only with your own time (for setup and maintenance) and build the review step yourself. They suit teams that already have a CI with artifacts, want the state in git and don't worry about a bit of additional coding burden.

Hosted services take screenshots or DOM snapshots and compare, store and show them on their side. You get a review UI, PR integration, baseline history and cross-browser rendering on day one. In exchange you pay per screenshot, depend on the service for every run and your baselines live outside the repository. They suit teams who want the workflow without building it and teams with many contributors on different machines.

Self-hosted services (reg-suit on your own S3 bucket) sit in between: the service model without the vendor.

### 3. How much noise can you remove at the source?

If you can run comparisons in a pinned renderer, a local tool with repository baselines is stable and cheap. If you cannot (many contributors on many OSes, no Docker in CI), a service that renders on its side removes the problem by taking rendering away from you.

### 4. What do you need to read back?

Teams rarely ask this one and often regret it. Once the run is over, something has to tell the reviewer what failed and where the images. Tools that leave only image folders force you to walk directories. Tools that write a machine-readable result (a JSON report, CTRF, the [manifest](/manifest)) let you build the PR comment, the approval job or the dashboard once and keep it when you switch tools. Hosted services keep the results inside their app, which is convenient until you want them elsewhere. The table above shows this for every tool.

### Reasonable defaults

- Playwright users: start with `toHaveScreenshot`, a pinned Docker image and baselines in the repository. Add a review step (PR comment or viewer) from the JSON reporter output, which converts to a manifest.
- Cypress users: a plugin that compares in the runner and shows the diff in the Cypress UI. `pixsame` writes the manifest natively, `cypress-image-snapshot` and `cypress-visual-regression` have converters.
- Storybook users: `Lost Pixel` or `Loki` locally, `Chromatic` if you want the hosted review and can pay per snapshot.
- Don't want to use full E2E tool like Playwright/Cypress: `BackstopJS`, which needs only a list of URLs or a hosted service with a static upload.
- Mobile: the per-platform tool your framework recommends. `Roborazzi` writes a JSON summary, which makes it the easiest to integrate into review tooling.

### Keep the exit open

Whatever you choose, keep two things in your control: the baselines (export them, or keep them in git) and the results format (a file you can read without the vendor). A tool that writes or converts to the [manifest](/manifest) can be swapped for another one without changing the review step.

## Adding or correcting a tool

Open a pull request with a YAML file under `apps/site/data/tools/`. Every field is validated at build time, every claim needs a source URL from the tool's own documentation, and `lastVerified` is the day you checked. Vendor contributions are welcome and are held to the same standard as everyone else's.

For the calculator, add or fix `apps/site/data/pricing/<tool>.yml` (same file stem as the tool). Take every number from the vendor's pricing page, set `fetchedAt` to the day you read it, `confidence` to how directly the page states the numbers, and put anything a reader needs to interpret them in `notes`; leave plans the page prices as "contact us" with `monthly: null`. Then run `pnpm --filter @visual-regression/site pricing:fetch --accept --only <tool>` to record the page hash, so the next refresh knows which version of the page the numbers match. The schema is `pricingSchema` in `apps/site/content.config.ts`.
