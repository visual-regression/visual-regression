Every row is one YAML file in the repository, with a date it was last checked and links to the vendor's own documentation for each claim. The comparison shows the pricing model only, because numbers are the first thing to go stale; the [calculator below](#estimate-the-cost) uses dated numbers from a separate data set that a script refreshes from the vendors' pricing pages, and every row there shows when it was checked. Select a tool (the chevron marks every row that opens) for the details, the sources, and a link to correct it.

The detail most comparisons leave out is machine-readable results: what a tool running _after_ the tests can read. Most tools leave you image folders and nothing else, hosted services keep the results inside their app, and a few write a JSON report. The manifest entry says whether a tool writes the [run manifest](/manifest) itself, has a converter in `visual-regression-manifest`, or fits the generic image-triple converter.

## How to read it

- Hosting: where the comparison happens. _Local_ tools diff on the machine running the tests; _cloud_ services take screenshots or DOM snapshots and diff on their side; _self-hosted_ means you run the service.
- Review (in the details): where a human looks at the diff. _Local files_ means opening the images yourself; _pull request_ means a comment or check on the PR; _web app_ means the service's own UI.
- Baselines (in the details): where the reference images live. In the repository they version with the code; in a service they version with the service's notion of a branch.
- Pricing: free, a free tier with paid plans, per screenshot, per seat, or a custom quote. The numbers are in the calculator below.

## Estimate the cost

Enter what your suite produces and the table shows, for every tool above, the plan that holds that volume and what it costs per month. Tools that run on your own CI cost runner time instead, estimated from the CI price and the seconds per screenshot you enter. pixsame is a free local plugin today; its hosted renderer is in preparation and is not priced.

:cost-calculator

The numbers come from `apps/site/data/pricing/<tool>.yml`, one file per tool that is not free, each holding the vendor's plans (price per month, included screenshots or seats, overage price), the date they were read from the pricing page, a confidence level, and a hash of the page text they came from. `scripts/fetch-pricing.mjs` fetches every pricing page, compares the hash and, for pages that changed, asks Claude to extract the plans again from the page text alone (`--check` only reports the changes; `--only <tool>` limits the run). A maintainer runs it by hand now and then and checks the result against the pages before opening a pull request. Applitools' page sits behind a bot check, so its numbers are read in a browser and its hash stays empty.

## Adding or correcting a tool

Open a pull request with a YAML file under `apps/site/data/tools/`. Every field is validated at build time, every claim needs a source URL from the tool's own documentation, and `lastVerified` is the day you checked. Vendor contributions are welcome and are held to the same standard as everyone else's.

For the calculator, add or fix `apps/site/data/pricing/<tool>.yml` (same file stem as the tool). Take every number from the vendor's pricing page, set `fetchedAt` to the day you read it, `confidence` to how directly the page states the numbers, and put anything a reader needs to interpret them in `notes`; leave plans the page prices as "contact us" with `monthly: null`. Then run `pnpm --filter @visual-regression/site pricing:fetch --accept --only <tool>` to record the page hash, so the next refresh knows which version of the page the numbers match. The schema is `pricingSchema` in `apps/site/content.config.ts`.
