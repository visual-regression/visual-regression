[How image diffing works](/learn/how-image-diffing-works) explains the two limits every tool exposes: a color tolerance per pixel and a maximum diff ratio per image. This deep dive is about the code behind them. There are fewer engines than tools: most JavaScript runners share one algorithm in several ports, the native frameworks each have their own, and the hosted services describe theirs only in their documentation. Knowing which one sits under your tool tells you what its threshold means, why anti-aliasing does or does not show up in your diffs, and when a different engine would answer your question better.

## What every engine decides

Every comparator answers the same three questions, and the engines differ in how:

1. **Are these two pixels the same color?** A color metric turns two RGBA values into a distance and a tolerance decides how far apart "the same" may be. The metric sets the scale of the tolerance, which is why `0.1` in one tool is not `0.1` in another.
2. **Is this differing pixel just anti-aliasing?** Text and diagonal edges are drawn with partially covered pixels whose exact values depend on the font engine and the rasterizer. An engine either detects such pixels and ignores them, offers a blunter tolerance instead, or counts them.
3. **How much is too much, and what do I report?** A count of differing pixels, a percentage, a boolean with bounding boxes, a similarity score, or a verdict from a service. The maximum diff ratio of the learn chapter is only meaningful where the engine reports a count.

A fourth, smaller question is what happens when the images differ in size: a thrown error, a failed comparison with a diff image anyway, or a comparison of the overlapping region.

## pixelmatch

[pixelmatch](https://github.com/mapbox/pixelmatch) is the reference implementation for the JavaScript ecosystem: a single file with no dependencies that works on raw RGBA typed arrays and returns the number of mismatched pixels. The README used to say "around 150 lines"; today it says "a few hundred", and the current source is about six hundred lines, most of them optimization.

```js
import pixelmatch from 'pixelmatch';
const count = pixelmatch(img1.data, img2.data, diff.data, width, height, { threshold: 0.1 });
```

**Color metric.** Up to version 7, pixelmatch converts both pixels to the YIQ color space (NTSC luminance plus two chroma axes), weights the squared differences (`0.5053·ΔY² + 0.299·ΔI² + 0.1957·ΔQ²`) and compares the result with `35215 · threshold²`, 35215 being the largest value that metric can produce (black against white). The `threshold` option (0 to 1, default `0.1`) is therefore a fraction of the black-white distance, with a squared relation: `0.1` allows about one hundredth of the maximum weighted distance. Luminance differences weigh most, which matches how eyes work, and semi-transparent pixels are blended against a background before the comparison (white up to version 7.1, a per-pixel checkerboard since 7.2, so that two colors that only look alike over white do not pass).

Version 8.0.0 replaced YIQ with the [OKLab](https://bottosson.github.io/posts/oklab/) color space and the HyAB distance (the absolute lightness difference plus the Euclidean chroma distance), a metric that tracks perceived differences much better across the whole gamut. The `threshold` scale is unchanged, `1` is still black against white and `0.1` still the default, but the counts differ, so a baseline suite moving to version 8 re-measures its tolerances. At the time of writing every tool that embeds pixelmatch still runs a YIQ-era copy, which the [table below](#the-engines-side-by-side) records.

**Anti-aliasing.** With `includeAA: false` (the default) a differing pixel is checked by the detector from Vyšniauskas's 2009 paper "Anti-aliased pixel and intensity slope detector": look at the 8 neighbors; if more than two are identical to the pixel it is not anti-aliasing; if there is no darker *and* no brighter neighbor it is not anti-aliasing; otherwise, if the darkest or the brightest neighbor has three or more identical siblings in *both* images, the pixel sits on an intensity slope between two flat areas and counts as anti-aliased. Such pixels are painted yellow in the diff image and not counted. The check runs on both images, so a pixel that is anti-aliased in either is excluded.

**What it reports.** The count of differing pixels (and, since 8.0.0, optionally the largest count inside any `windowSize`×`windowSize` square, so that noise scattered across the image stays low while a compact change stands out). A ratio is up to the caller: `count / (width × height)`. An `ignoreMask` (8.0.0) skips regions by a per-pixel mask. Images of different sizes throw.

**Speed.** One pass in JavaScript with a fast path for identical images; fast enough that the PNG decode usually costs more than the comparison. Tools that found it slow on full-page screenshots went to odiff or to a block-optimized port such as `@blazediff/core`.

**Used by** Playwright (a vendored 2019 copy with the default `threshold` raised to `0.2`), jest-image-snapshot (`^5.1.0`, with its own default `threshold` of `0.01`), `@pixsame/cypress-plugin-visual-regression-diff` (`7.2.0`, passing `diffConfig` straight through), Lost Pixel (`5.3.0`, called with `threshold: 0`), Loki's default engine (`^5.2.0`), the old reg-cli engine, and Vitest through a reimplementation (below).

## odiff

[odiff](https://github.com/dmtrKovalenko/odiff) is the same algorithm compiled to a native binary: originally OCaml, now Zig with SIMD paths for SSE2, AVX2, AVX-512 and NEON. Its color delta uses pixelmatch's YIQ coefficients and the same `35215 · threshold²` limit, and its anti-aliasing detector is the same sibling test, so a given `threshold` means the same thing in both. It decodes PNG, JPEG, WebP, TIFF and BMP itself, which is where much of the speed comes from: the README's benchmark on full-page screenshots puts it at about six times faster than pixelmatch and ImageMagick's `compare`.

What it adds over pixelmatch is operational: **ignore regions** (`--ignore x1:y1-x2:y2,...`, `ignoreRegions` in the Node binding), a `--fail-on-layout` switch that turns a size mismatch into a distinct result instead of a thrown error, a `--diff-mask` output, diff line numbers, a parsable stdout format, and a long-running server mode for tools that compare thousands of images. The Node package `odiff-bin` returns `{ match: true }` or `{ match: false, reason: 'pixel-diff', diffCount, diffPercentage }` (or `reason: 'layout-diff'`), so the ratio comes with the result.

**Used by** Argos (its server-side comparison), Lost Pixel (as the optional `compareEngine: 'odiff'`), and many homegrown pipelines where pixelmatch was the slow part.

## Resemble.js

[Resemble.js](https://github.com/rsmbl/Resemble.js) predates pixelmatch, runs in the browser (canvas) and in Node (node-canvas), and reasons in RGB rather than a perceptual space.

**Color metric.** Each channel has its own integer tolerance; by default red, green, blue and alpha may differ by up to 16 (on a 0 to 255 scale), plus a brightness rule (`0.3·R + 0.59·G + 0.11·B`) with `minBrightness: 16` and `maxBrightness: 240`. Two pixels are "similar" when every channel is within tolerance. The `ignore` presets change the numbers: `nothing` sets every tolerance to 0 (exact match), `less` is the default set above, `antialiasing` widens the channels to 32 and turns the anti-aliasing logic on, `colors` compares brightness only (so a hue change passes), and `alpha` ignores the alpha channel.

**Anti-aliasing.** With `ignoreAntialiasing`, a pixel is considered anti-aliased when, among its 8 neighbors, more than one is strongly contrasting or more than one differs in hue by more than 0.3, or fewer than two are identical to it; such pixels are then compared by brightness alone. It is a blunter rule than the slope detector, and on large images (either side above `largeImageThreshold`, default 1200 px) the anti-aliasing pass only samples every sixth row and column to stay fast.

**What it reports.** `misMatchPercentage` (a string with two decimals, the share of differing pixels), `rawMisMatchPercentage` (the full number), `isSameDimensions` and `dimensionDifference` (it compares anyway), `diffBounds`, `analysisTime`, and a diff image whose style is configurable: `errorType` `flat` (solid color), `movement` (blended with the second image), `flatDifferenceIntensity`, `movementDifferenceIntensity` or `diffOnly`, plus `boundingBox` and `ignoredBox` regions. `scaleToSameSize` resizes before comparing.

**Used by** BackstopJS, through a fork of the Node port (`@mirzazeyrek/node-resemble-js`). Backstop's per-scenario `misMatchThreshold` is Resemble's percentage (default `0.1`, meaning 0.1% of the pixels), `requireSameDimensions` (default `true`) turns a size change into a failure, and `resembleOutputOptions` passes the diff-image settings and `ignoreAntialiasing` through. Because `misMatchPercentage` is rounded to two decimals, Backstop offers `usePreciseMatching` for thresholds below 0.01%.

## looks-same

[looks-same](https://github.com/gemini-testing/looks-same) comes from the Gemini/hermione line of tools and is the one JavaScript engine built on a standard perceptual color-difference formula.

**Color metric.** Non-strict mode converts both pixels to CIE L\*a\*b\* and computes CIEDE2000; two colors are the same when the distance is below `tolerance`, whose default `2.3` is the just-noticeable difference (the library's constants call it `JND`). A cheap CIE76 bound is computed first to skip the expensive formula for clearly equal or clearly different pairs. `strict: true` requires exact RGB equality instead and rejects a `tolerance`.

**Anti-aliasing and the caret.** `ignoreAntialiasing` (default `true`) implements the same Vyšniauskas detector as pixelmatch, with an `antialiasingTolerance` (default `0`) for the minimum brightness difference between the darkest and lightest neighbor; the README advises not to raise it above 10. `ignoreCaret` (default `true`) is unique to this engine: it recognizes the thin vertical bar of a blinking text cursor and ignores it, so a screenshot taken with a caret on and one with it off compare equal.

**What it reports.** `{ equal, diffBounds, diffClusters }`, where clusters (`shouldCluster`, `clustersSize`, default 10) group nearby differing pixels into rectangles a reviewer can read as "three things changed"; with `createDiffImage: true` also `differentPixels`, `totalPixels` and the image. `looksSame.createDiff` renders the diff with a `highlightColor`. There is no maximum diff ratio: the result is a boolean plus where.

**Used by** testplane (the renamed hermione; its own defaults are `tolerance: 3.0` and `antialiasingTolerance: 4`), the earlier Gemini, and Loki's optional `looks-same` engine.

## blink-diff

[blink-diff](https://github.com/yahoo/blink-diff), from Yahoo in 2014, is archived and no longer used by current tools, but its ideas survive in the others. Its color distance was the plain Euclidean distance over the four RGBA channels, with `delta` (default 20) as the tolerance; a `perceptual` mode converted through gamma correction and XYZ to CIE L\*a\*b\* instead. It had no anti-aliasing detector; instead `hShift` and `vShift` (default 2) let a pixel match any pixel within a small window, which absorbs sub-pixel shifts and most anti-aliasing at the price of missing one-pixel changes. Its threshold was either a pixel count (`thresholdType: 'pixel'`, default 500) or a percentage, and its output was the three-panel composition (approved, diff, build) that jest-image-snapshot and Roborazzi later adopted. The pixelmatch README credits it and Resemble.js as inspiration. The shift-window idea reappears in Dropbox's differ and in Paparazzi's default "off by two" comparator.

## SSIM

The [structural similarity index](https://en.wikipedia.org/wiki/Structural_similarity_index_measure) (Wang et al., 2004) does not compare pixels at all. It slides a window (11×11 by default) over both images and, for each position, compares the local mean (luminance), the local variance (contrast) and the correlation (structure) of the two patches; the per-window scores form a map and their mean is the result, `1` for identical images. It was designed to predict how humans rate image quality, which makes it good at the things pixel counts are bad at: JPEG or WebP compression artifacts, slight blur, noise, and sub-pixel shifts all leave the structure intact and score near `1`.

[ssim.js](https://github.com/obartra/ssim) is the JavaScript implementation the tools use. It offers four algorithms: `original` (a line-by-line port of the reference MATLAB code), `fast` (mathematically equivalent, quicker), `bezkrovny` (downsamples first; close to but not identical with the original) and `weber` (the fastest, also approximate, and the library's current default). It returns `mssim`, the map and the time taken.

**In the tools.** [jest-image-snapshot](https://github.com/americanexpress/jest-image-snapshot) exposes it as `comparisonMethod: 'ssim'` (default `'pixelmatch'`), with `bezkrovny` as its default algorithm and the advice to set a 1% threshold for SSIM comparisons; its README describes the benefits as fewer false positives and higher sensitivity to real changes, and the cost as floating-point work that does not benefit from the pixel-count fast paths. Paparazzi has an `mssim` differ. Playwright's source contains an undocumented `ssim-cie94` comparator (set through a private `_comparator` option): a pixel passes if its CIE94 ΔE is at most 1, otherwise it is treated as anti-aliasing when the SSIM of a 31×31 window around it is at least 0.99, and counted as a difference otherwise. It is not part of the public API.

**Where SSIM fails.** It is computed on luminance, so a change that keeps structure and only shifts color can score very high; Playwright's test fixtures include an "SSIM trap", a white image and a gray image that some color-weighted SSIM variants report as equal. A small change (a one-character typo) inside a large window is averaged away by everything around it that still matches, so a global `mssim` of 0.999 can hide exactly the regression a text-heavy UI cares about. It localizes less sharply than a pixel diff, it is slower, and its score is not a count, so "0.5% of the pixels may differ" has no SSIM equivalent. The honest use is an image that is expected to differ in rendering details but not in content: charts, photos, canvases, scaled images.

## Perceptual hashes

A perceptual hash reduces the whole image to a short fingerprint. [pHash](https://www.phash.org/docs/design.html) downscales to grayscale, takes a discrete cosine transform, keeps the low frequencies and encodes which are above the median into a 64-bit value; two images are compared by the Hamming distance between their hashes, the number of differing bits. [blockhash](https://github.com/commonsmachinery/blockhash-js) does the same with block mean values instead of a DCT. Both are robust to scaling, compression, small rotations and blur, which is what they were built for: finding copies and near-duplicates in large collections.

That robustness is exactly why they do not fit regression testing. A hash cannot say *where* the difference is, and a changed label, a missing icon or a wrong number in one table cell moves at most a bit or two, well inside the distance that scaling noise also produces. They fit a coarse question ("is this the same screenshot family, or did the page change completely?"), de-duplication of baselines, or a first cheap pass before a real comparison. Among visual regression tools, VexFlow's test suite uses a pHash distance with a threshold to flag changed renderings; the mainstream web tools do not use hashing as their engine.

## The native tools

**Roborazzi** (Android) delegates to Dropbox's [differ](https://github.com/dropbox/differ) library. Its `SimpleImageComparator` computes the Euclidean distance between two RGBA colors and counts a pixel as different when the distance exceeds `maxDistance` (differ's own default is `0.001`; Roborazzi's default comparator uses `0.007`), with optional `hShift`/`vShift` windows, the blink-diff idea, which the README suggests increasing to work around anti-aliasing. Roborazzi's `changeThreshold` is the maximum diff ratio: a `ThresholdValidator` fails when more than that fraction of the pixels differ (default `0`). The comparison writes a composite image (`[name]_compare.png`) and a `results-summary.json`, the input of the [manifest converter](/manifest/converting).

**swift-snapshot-testing** (iOS/macOS) has two numbers with similar names and different jobs. `precision` is the fraction of pixels that must match (default `1`). `perceptualPrecision` (default `1`) is the per-pixel color tolerance: below `1`, each pixel is compared with Core Image's `CILabDeltaE` filter and passes when its ΔE is at most `(1 − perceptualPrecision) × 100`, so `perceptualPrecision: 0.98` allows a ΔE of 2, and the docs say that `0.98` to `0.99` "mimics the precision of the human eye". With both at `1` any differing byte fails. There is no anti-aliasing detection; the perceptual tolerance plays that role.

**Flutter golden tests** are the strictest of all: `matchesGoldenFile` with the default `LocalFileComparator` decodes both PNGs and requires an exact match. A pixel differs when the sum of the absolute channel differences is non-zero; the result reports `diffPercent` (a fraction, despite the name) and, on failure, writes four images (`masterImage`, `testImage`, `isolatedDiff`, `maskedDiff`). A size mismatch fails with 100%. There is no tolerance in the framework, but the `goldenFileComparator` documentation shows the pattern for one: a subclass whose `compare` accepts `diffPercent` below a chosen value. Flutter's test font (Ahem) and software rendering are what make exact matching workable in the first place.

**Paparazzi** (Android, JVM rendering) ships several differs selectable by a system property: `offbytwo` (the default; a pixel may differ by a small amount, the cross-platform workaround), `pixelperfect`, `mssim`, `sift`, `flip` and `de2000`, with `maxPercentDifference` (default `0.01`, in percent) as the limit.

## The hosted services

The services compare on their servers and document the knobs, not the code. What follows is what their public docs state.

- **Applitools** exposes *match levels*. **Exact** is a pixel-to-pixel comparison the docs do not recommend for ordinary use. **Strict** is the default and, per the docs, most effective for regression tests on one browser and OS with mostly static content; it is described as a perceptual comparison. **Content** (now named **Ignore Colors**) is Strict without color differences. **Layout** compares the structure and relative positioning of elements and is meant for dynamic content. The recommended practice is Strict globally with Layout or Ignore Colors regions where needed.
- **Chromatic** measures color difference in the YIQ color space between the same coordinates in both snapshots; `diffThreshold` (0 to 1, default `0.063`) is the per-pixel tolerance, settable per project, component, story or test. It detects anti-aliased pixels and ignores them unless `diffIncludeAntiAliasing: true`. `pauseAnimationAtEnd`, `delay` and `cropToViewport` control the capture, not the comparison.
- **Percy** documents capture options (`widths`, default 375 and 1280; `minHeight`, default 1024; `percyCSS`; `enableJavaScript`) and region algorithms: `standard` (pixel-based, with strictness presets and a `diffSensitivity`), `layout`, `ignore`, and `intelliignore` for images, with a diff-sensitivity slider whose default is 20%. The underlying pixel algorithm is not described.
- **Argos** states that it runs odiff twice with anti-aliasing detection on: a tolerant pass (color threshold `0.15`, discarded when fewer than 20 pixels or 0.02% of the image changed) and a color-sensitive pass (`0.0225`, counted only when at least 3% of the image changed); the higher score wins. Its `threshold` (0 to 1, default `0.5`) scales those tolerances: `0` is zero tolerance, `1` doubles them.

Three self-hosted or local tools with their own wrapping belong in the same list: **Lost Pixel** (`threshold` below 1 is a ratio, 1 or above a pixel count, default `0`; `compareEngine` `pixelmatch` or `odiff`), **reg-suit/reg-cli** (a Rust port of pixelmatch's YIQ comparison compiled to WebAssembly; `matchingThreshold` is the color tolerance, default `0`; `thresholdRate` or `thresholdPixel` the maximum; anti-aliasing detection is off unless `enableAntialias` is set), and **Loki** (three engines: pixelmatch by default, GraphicsMagick's `compare`, or looks-same).

## How to choose

**Text-heavy UIs.** Anti-aliasing detection is the feature that matters: without it, every letter edge is a candidate difference. The pixelmatch family (pixelmatch, odiff, blazediff, Chromatic's comparison) and looks-same have the slope detector; Resemble's rule is coarser and sampled on large images; SSIM dilutes a changed word inside its windows; Flutter and swift-snapshot-testing have none and rely on a pinned renderer. Pick a detector-equipped engine *and* [pin the renderer](/cookbook/pin-the-renderer): the detector removes the pixels that sit on the slope, not the glyphs that were hinted differently.

**Compression artifacts and resampled images.** Pixel engines see JPEG blocks and scaling noise as thousands of small differences; raising the color tolerance hides a tint change along with them. SSIM is the right instrument here because the structure survives the artifact, and a per-region color tolerance (looks-same's ΔE, swift-snapshot-testing's `perceptualPrecision`) is the second-best. Better still is to avoid the problem: screenshot as PNG, never scale before comparing.

**Cross-browser and cross-OS.** No engine solves this; rendering differences are real differences. What helps is an engine that reports *where* (looks-same's clusters, odiff's diff lines, any diff image) so a reviewer can tell a hinting change from a layout change quickly, a layout-aware mode (Applitools' Layout level) when the question is "did anything move", and separate baselines per platform, which the [manifest](/manifest) records as `platform` and `renderer`.

**Why the two limits mean different things per engine.** The color tolerance of the learn chapter is pixelmatch's `threshold` (a fraction of the black-white distance, squared in YIQ versions), Resemble's per-channel integers, looks-same's ΔE units, swift-snapshot-testing's `1 − ΔE/100`, differ's RGBA distance, Chromatic's YIQ fraction; the same `0.1` is strict in one and meaningless in another. The maximum diff ratio exists only where the engine counts: pixelmatch and odiff count pixels, Resemble reports a percentage, looks-same reports a boolean with clusters, SSIM a similarity score, the services a verdict. That is why the manifest stores the tolerance together with the metric it belongs to (`comparison.colorMetric`, `comparison.colorThreshold`) and stores the ratio only where the writer knows it (`comparison.maxDiffRatio`, `comparison.diffRatio`), and why a tolerance copied from one tool's docs into another's config is a guess.

## Try them yourself

The [online diff tool](https://diff.visual-regression.dev) takes two images and compares them with several of the engines above side by side, with their options exposed, so you can watch the same pair of screenshots pass one engine and fail another before you commit to a tolerance.
